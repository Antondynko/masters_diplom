# Тестирование

```bash
python -m unittest discover -s ./tests -v          # все тесты
python -m unittest tests.e2e.test_metamorphic -v       # метаморфные
python -m unittest tests.e2e.test_golden -v            # эталонные
```

## Зачем нужны e2e-тесты и в чём трудность

Unit-тесты (`test_follower`, `test_leader`, `test_neighborhoods`, ...) проверяют функции по отдельности. Но ошибка может жить в том, как они связаны: например, `solve` может вернуть не то решение, которое нашёл локальный спуск, — каждая функция по отдельности при этом работает правильно.

Для e2e-теста нужен **оракул** — способ понять, что ответ правильный. Для приближённого алгоритма «правильный» не значит «оптимальный»: VND может остановиться в локальном оптимуме, который хуже глобального, и это корректная работа алгоритма, а не ошибка.

Ключевое наблюдение: **при заданном стартовом размещении алгоритм детерминирован.** Случайность есть только в `generate_y_start`. Окрестности `swap` и `swap_2` перебираются в фиксированном порядке (по возрастанию номеров предприятий), `follower` при равных предпочтениях выбирает предприятие с меньшим номером. Значит, из одного и того же старта всегда получается один и тот же путь поиска и один и тот же ответ. На этом построены оба вида e2e-тестов ниже.

## Эталонные тесты (`tests/e2e/test_golden.py`)

Фиксированный старт на `datasets/20_20_15.txt` (V = 47000) → заранее известный ответ. Для каждого случая проверяется:

- `test_value` — значение целевой функции V − f;
- `test_moves` — сколько шагов 1-swap и 2-swap было принято (что алгоритм прошёл тот же путь, а не пришёл к ответу случайно);
- `test_placement` — итоговое размещение y.

Случаи подобраны так, чтобы покрыть разное поведение: несколько циклов «спуск → 2-swap → спуск», случай без единого улучшения по 2-swap, разные p (5 и 10), а также старт, из которого VND приходит в **неглобальный** локальный оптимум (37043.70 при глобальном 37384.01 для p = 5).

### Откуда взяты ответы

Задача для каждого старта решена один раз, ответы записаны в тест константами. Сам тест ничего не вычисляет, а только сравнивает результат `solve` с записанным ответом. Так любое изменение кода, которое затронет поведение алгоритма, сразу будет видно.

Чтобы добавить новый случай, нужно один раз прогнать `solve` с выбранным стартом и `tracer=Tracer()`, проверить результат, взять из трейса число принятых шагов `swap1` и `swap2` и дописать строку в `GOLDEN`.

### Известная проблема

Если в `local_search` срабатывает ограничитель `max_iter`, возвращается вектор из одних нулей.

## Метаморфные тесты (`tests/e2e/test_metamorphic.py`)

Метаморфный тест не знает правильного ответа. Он меняет входные данные так, что **изменение ответа известно заранее**, и сравнивает два прогона: на исходных и на преобразованных данных. Сравнивается весь ход поиска: все вычисленные соседи по порядку (из `Tracer`), итоговый y и значение.

| Тест | Преобразование | Ожидание | Почему так |
|---|---|---|---|
| M1 `test_m1_shift_V` | V → V + k | тот же путь, значение + k | все сравнения идут по разности V − f, сдвиг V её не меняет |
| M2 `test_m2_scale_c_and_V` | c → a·c, V → a·V, a > 0 | тот же путь, значение × a | V − f умножается на a > 0, знаки сравнений сохраняются |
| M3 `test_m3_shift_c_per_client` | c[i][j] → c[i][j] + b_j | тот же путь, значение − Σb_j | каждый клиент назначен ровно одному предприятию, поэтому f сдвигается на Σb_j при **любом** y |
| M4 `test_m4_monotone_transform_d` | d[i][j] → g_j(d[i][j]), g_j строго возрастает | тот же путь, то же значение | у каждого клиента сохраняется порядок предпочтений, поэтому follower назначает так же |
| M5 `test_m5_permute_clients` | перестановка клиентов (столбцы c и d вместе) | тот же путь, то же значение | клиенты независимы, f — сумма по ним |

M3 и M4 отражают двухуровневую структуру задачи: верхний уровень реагирует только на разности затрат между предприятиями, нижний — только на порядок предпочтений, а не на их величины.

Проверено, что тесты действительно ловят нарушения: сдвиг затрат по предприятиям (а не по клиентам) и немонотонное преобразование d, например (d − 5)², меняют путь поиска на всех стартах.

Детали реализации:

- Старты — `generate_y_start` с фиксированными сидами. `test_starts_cover_swap2` проверяет, что хотя бы на одном старте 2-swap даёт улучшение: иначе вторая фаза алгоритма не проверяется.
- В M2 множители — степени двойки: умножение на них в float точное, и округление не может перевернуть сравнение.
- В M4 значения после преобразования должны оставаться меньше константы `2147483647` из `follower`.
- В M3 и M5 сумма считается в другом порядке, поэтому значение сравнивается с допуском, а y и путь — точно.

### Чего метаморфные тесты не проверяют

- Перестановка **предприятий** — не инвариант. Множество соседей то же, но меняется порядок перебора, и first-improvement примет другого соседа. Результат VND с first-improvement зависит от нумерации предприятий.
- Ошибки, которые одинаково проявляются на исходных и преобразованных данных, метаморфные тесты не ловят. Так было с ошибкой в `solve`, возвращавшей не то размещение: её поймали эталонные тесты.
